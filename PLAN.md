# prechips — plan (rev 2)

> Checks before chips. A deterministic checker that takes a part (STEP), a
> proposed process plan (YAML), a feature specification sidecar (YAML, from the
> CAD/drawing side) and one specific shop's inventory (YAML), and reports what it
> can prove, what it refutes, and what it cannot know — before a traveler is
> printed and before an LLM machinist review or a human sees it.

Status: plan only. No code beyond the package skeleton. Rev 2, 2026-10-02,
after the adversarial review in
[`docs/reviews/2026-10-02-plan-rev1-adversarial.md`](docs/reviews/2026-10-02-plan-rev1-adversarial.md).
Rev 1 claimed a gate that "proves executability"; it could not. Rev 2 narrows
to what a checker can establish from declared inputs, names unknowns as
unknowns, and defers geometry-heavy rules behind a kernel spike.

## 1. Why this exists

The harmonic-analyzer CAD pipeline produces 103 part drawings and 8 assembly
drawings, each gated by a blind LLM machinist review. Process knowledge —
stock, setups, workholding, order of operations — exists only as prose
(`cad/config/parts/*.yaml` `process:` strings; `cad/docs/machining-dfm.md`,
which is itself stale: it discusses a brass knife-mount while the registry now
specifies hardened O1). There is no traveler, and nothing checks a proposed
plan against geometry or against the shop that will run it.

The LLM review is the *last* layer of defense. It should receive a plan that a
deterministic checker has already run, with findings attached, so it judges
craft rather than catching arithmetic.

Two things shape the design:

- **The shop is manual-with-digital-positioning.** PM-30MV with a CNC
  conversion driven by cncjs, operated by hand through an XHC WHB04B-6 pendant
  and the EL400 DRO emulator (`pedropaulovc/el400`). Feeds are human; positions
  are read off a DRO. The lathe (PM-1127VF-LB) is manual. So the artefact to
  validate is a **per-setup coordinate table**, not a toolpath.
- **No CAM dependency.** Fusion is out (personal licence is non-commercial, the
  book/Kickstarter are commercial; GUI-bound; weak API signal). FreeCAD is the
  B-rep kernel, headless, behind a thin JSON adapter — and only once a spike on
  the consumer's real STEP exports shows it can do the job (§7, M2).

## 2. What a finding is

Every rule yields exactly one status per subject:

| status | meaning |
|---|---|
| `pass` | the declared inputs satisfy the rule |
| `fail` | the declared inputs violate the rule; severity `block` or `warn` |
| `unknown` | a required input is absent or carries `verify: true`; the rule could not run |
| `not_applicable` | the rule's precondition (operation class, machine kind) does not hold |

Exit codes: `0` only when no rule is `fail/block` **and** no *required* rule is
`unknown`. `unknown` on a required rule exits `4` ("not ready"), distinct from
`fail` (`2`). An unverified inventory therefore never produces a green exit;
it produces a list of measurements to take. Which rules are required is a
per-consumer setting (`required_rules:` in the plan), defaulting to the rank-1
and rank-2 rules in §4.

A rule specification is testable or it does not ship: units, applicability
predicate, exact inequality with boundary behaviour, source (edition/page or
URL+date), uncertainty treatment, one valid and one invalid example. A bare
"see Machinery's Handbook" is not a citation.

## 3. Inputs and contracts

### 3.1 `part.step` (+ `part.stl` for renders)

As exported by the consumer (`export_models.py`, AP214). **No PMI is assumed
in the STEP**: the consumer's export contract is colours, not semantic PMI, and
rev 1's PMI-coverage and datum rules had no input. Everything dimensional comes
from the sidecar below. Report records the STEP's SHA-256; a sidecar or plan
bound to a different STEP hash is a `block`.

### 3.2 `spec.yaml` — feature specification sidecar (consumer-authored)

Generated by the CAD side (harmonic-analyzer: from `_gtol_spec.py` and the
part registry, where the drawing annotations originate), never by prechips:

```yaml
part: rocker-arm
step_sha256: "…"
revision: v21
units: mm
frames:
  A: {origin: [0, 0, 0], axes: {x: [1,0,0], y: [0,1,0], z: [0,0,1]}, note: "bottom face, left edge, front edge"}
features:
  - id: hub_bore
    kind: hole            # hole | bore | shaft | slot | pocket | face | thread | fillet
    frame: A
    axis: [0, 0, 1]
    center: [25.4, 12.7, 0]
    diameter: {nominal: 6.35, upper: +0.015, lower: 0, source: "drawing sheet 1, zone B3"}
    depth: {nominal: through}
    finish: {ra_um: 1.6}
    datum_refs: []
  - id: pivot_tap
    kind: thread
    spec: "1/4-20 UNC-2B"
    full_thread_depth: 9.5
    blind: true
```

Fields the rules need and rev 1 did not have: typed feature kind (so "every
cylinder gets a drill op" no longer catches shafts and counterbores), explicit
frames, nominal + tolerance + decimal precision, blind-thread full-thread depth.

### 3.3 `plan.yaml` (author: machinist / agent, reviewed by the gate)

```yaml
part: rocker-arm
spec: spec.yaml
stock:
  form: flat_bar
  material_spec: "1018 CRS"
  section_mm: {w: 25.4, t: 9.525}
  length_mm: 60
  cut_allowance_mm: 1.0
setups:
  - id: S1
    machine: PM-30MV
    workholding: {kind: vise, ref: vise-pm-6, parallels: parallels-lms-6745, parallel_height_in: 0.75}
    frame: A                          # from spec.yaml
    frame_setup: {origin_touch: ["edge_finder: left face -> X0", "edge_finder: front face -> Y0", "paper: top -> Z0"]}
    features: [hub_bore, pivot_tap, profile_outer]
    operations:
      - {op: 10, do: face,  tool: endmills-lms-6784/1-2in-4fl, rpm: 1200}
      - {op: 20, do: spot,  feature: hub_bore, tool: center-drills-lms-4859/2}
      - {op: 30, do: drill, feature: hub_bore, tool: drill-index-115/15-64, rpm: 1500}
      - {op: 40, do: ream,  feature: hub_bore, tool: reamers/0.2510, rpm: 500, check: "0.2510 pin gauge"}
verification: {status: planned}       # planned | bench_verified: {entry: logbook/entries/…}
required_rules: [schema, inventory_refs, sizing_tool, op_order, blind_thread_depth, envelope]
```

Tool references are `set/item`, resolving to one physical tool with its own
flute length, OAL, shank. Face lists are gone; features come from the sidecar.
(Rev 1's example was not even valid YAML: unquoted commas inside flow
sequences split each descriptor into two strings.)

### 3.4 `inventory.yaml` (user-supplied; sample in `examples/inventory/`)

Per-tool entries, not only sets. A set entry (`endmills-lms-6784`) expands to
items with per-item geometry (`diameter`, `flute_length`, `oal`, `shank`,
`flutes`, `center_cutting`) — vendor-page values flagged `verify: true` until
measured. Machine entries carry measured envelopes separately from vendor
claims (`travel_in` vs `travel_measured_in`). `present: null` is `unknown`, not
absent.

Unit handling: comparisons normalize to mm with the delta reported in both
units; substitution never happens. Example: spec Ø6.500 H7 vs nearest inch
reamer 0.2510 in = 6.3754 mm → `no_sizing_tool(hub_bore, nearest: reamers/0.2510, delta: −0.125 mm)` at `block`.

### 3.5 Outputs

- `report.json`: canonical (sorted keys, fixed float formatting, no
  timestamps), `{inputs: {step_sha256, spec_sha256, plan_sha256, inventory_sha256, rules_version}, findings: [{rule, subject, status, severity, evidence, cite}], hash}`.
  The hash covers the canonical JSON only — never rendered bytes.
- `traveler.html` / `traveler.pdf`: setups, operations, coordinate tables,
  findings inline; rendered bytes are *not* part of the determinism contract.
- `coordinates/<setup>.csv`: neutral per-setup coordinate table (feature id,
  X, Y, Z in the setup frame, op). **No EL400 preset format.** EL400 today
  mirrors cncjs position state and discards SDM sessions on exit; it has no
  import contract to couple to. An adapter is added only after a neutral table
  has been used at the machine.
- `setup-<n>.png`: optional, M3+.

## 4. Rule catalogue, ranked by expected signal

Ranks are engineering judgment for lots of 1–20, to be re-measured on the
pilot plans (warning burden on known-good plans is a tracked number).

| rank | rule | needs | status |
|---|---|---|---|
| 1 | `schema`, `inventory_refs`, `citations_present`, `step_binding` | plan, inventory, spec | M1 |
| 1 | `sizing_tool` — every hole/bore/thread feature with a tolerance has a tool that produces that size (reamer/tap/boring bar range); unit mismatch reported, never converted | spec, inventory | M1 |
| 2 | `hole_op_chain` — per feature kind: hole → spot/drill (→ ream \| → tap with tap drill from thread spec); bore → drill → bore; counterbores excluded from "every cylinder" | spec, plan | M1 |
| 2 | `op_order` — rough before finish, drill before ream/tap, face before spot | plan | M1 |
| 2 | `blind_thread_depth` — drill depth ≥ full-thread depth + tap chamfer lead + drill-point allowance; tap flute ≥ full-thread depth; breakout check against the opposite face | spec, inventory (tap geometry), plan | M1 |
| 3 | `envelope` — part+fixture inside measured travels; **spindle-to-table stack**: vise + parallels + part + tool holder + tool OAL ≤ `spindle_to_table_max`; drill feature depth ≤ quill stroke or declared knee/head move; chuck jaw swept diameter vs swing; stick-out behind headstock for bar work; parting blade radial reach ≥ stock radius; tailstock/saddle clearance for the declared tool | plan, inventory (measured), spec | M1 |
| 3 | `holder_compat` — tool shank fits a listed holder on the setup's machine (R8 collet sizes, QCTP holder shank cap, MT3 sleeve for the 2MT chuck) | plan, inventory | M1 |
| 3 | `index_representable` — dividing-head/rotary angle reachable with the listed plates within the feature's angular tolerance | spec, inventory | M1 |
| 4 | `coordinate_table` — feature coordinates in the setup frame derived from the sidecar; sign/offset cross-check against the plan's touch-off sequence; printed per setup | spec, plan | M1 |
| 5 | `tool_reach`, `fixture_collision`, `internal_corner_radius` — restricted to named milling operation classes with measured cutter/holder envelopes and explicit intermediate stock; `unknown` otherwise | STEP + kernel | M2/M3 |
| 6 | `grip`, `thin_wall_in_grip`, `part_off_last`, `tiny_part_method` — advisory (`warn`) | STEP + kernel, plan | M3 |
| 7 | `rpm_from_sfm`, `stickout_ld`, `engagement` — advisory with cited tables; RPM clamped to machine range | plan, inventory, cited tables | M3 |
| 8 | `coverage`, `axial_accessibility` — advisory; "as-stock" waiver must name faces | STEP + kernel | M3, maybe never |
| — | datum/re-fixture budget, PMI finish coverage | semantic PMI | dropped (no input) |
| — | deflection-vs-tolerance gate, tool-life counter, stock "winner" | calibrated force/clamp models | dropped as gates; see §5 |

Mutation controls: for each shipped rule, one known-bad plan that must `fail`
*and* one known-good plan that must `pass` (a checker that always fails would
otherwise satisfy "known-bad fires").

## 5. What stays advisory or deferred, and why

- **Physics proxies.** Rev 1's `F·L³/(3EI)` and `F·L³/(48EI)` assume a prismatic
  beam with an end/central load; `cone-gear-shaft` is stepped, the tool load
  moves, the tailstock is compliant, and Sandvik's specific cutting force is
  the tangential component, not the radial one that sets diameter error (and
  a radial deflection doubles diametrally). No clamping-force input exists.
  Kept only as an advisory estimate labelled as such, with a stated model and
  its assumptions, never a gate. Chatter/FRF: out.
- **Stock-form comparison.** Geometry can compute a declared blank's waste; it
  cannot synthesize setup routes, casting allowances, brazing acceptance or
  procurement cost. Replaced by an *authored* candidate table: the plan author
  lists candidate routes (hog from Ø75 bar, offset-turn on faceplate, built-up
  boss, outsourced casting) with their setups and fixtures; prechips reports
  waste volume, setup count, rule findings and unknowns per candidate as an
  unweighted table. No winner is declared; "indexed on a BS-0" is reported as
  3+1 indexing, never as "4-axis".
- **FreeCAD kernel.** Candidate APIs: `Part.Shape.read`, `Face.Surface`
  descriptors, `distToShape`/`common` against placed fixture solids, `section`
  against finite ray edges. OCC documents tangency/tolerance failures on
  booleans, and face ordering is not stable across versions. A spike on the
  consumer's actual STEP exports (M2) must show stable descriptor resolution,
  bounding boxes and one operation-specific reach check before any rank-5+
  rule is specified further. If the spike fails, M3 is cut and prechips stays a
  plan/inventory/coordinate checker.
- **Determinism.** Pinned: FreeCAD version *and bundled OCC*, importer
  settings, sampling algorithm and seed, numerical tolerances, rules version,
  JSON canonicalization. Feature identity comes from the sidecar ids, never
  from OCC object hashes. Renders and PDFs are excluded from the hash.
- **CAM simulation, EL400 adapter, cncjs macros, every fixture family.**
  After a neutral traveler has been used at the machine.

## 6. Architecture

```
uv venv (prechips)                              FreeCADCmd (M2+, optional)
---------------------------------               ------------------------------
spec.yaml + plan.yaml + inventory.yaml          STEP load, face descriptors,
      │                                          bounding boxes, fixture solids,
      ├─► schema / lint / rank 1–4 rules         distance & collision
      ├─► coordinate tables (csv)           ◄──► JSON job / JSON facts
      ├─► report.json (canonical, hashed)
      └─► traveler.html/pdf (not hashed)
```

- The uv side never imports a CAD kernel; it shells to `FreeCADCmd` with a
  JSON job and reads JSON facts. Absent kernel ⇒ kernel-backed rules are
  `unknown`, the rest run.
- Booleans stay local; state crosses boundaries as enums (`status`,
  `workholding.kind`, `verification.status`).

## 7. Milestones

Pilots (current revisions; the rev-1 `pivot-bushing` was retired 2026-09-02
when the rocker and lever got integral hubs):

- `rocker-arm` — ×20, 1018, integral hub bore, profile from flat bar (mill).
- `amplitude-bar` — ×20, steel bar with slide features (mill).
- `cone-gear-shaft` — ×1, stepped shaft between centres (lathe).
- `knife-mount` — ×2, O1 hardened 58–60 HRC: machine soft → heat-treat →
  finish; the plan must sequence the heat-treat and name the post-HT ops.

1. **M1 — plan/inventory/coordinate checker.** Schema, rank 1–4 rules,
   sidecar contract and a generator stub on the consumer side, coordinate
   tables, `report.json`, traveler. Controls: missing sizing tool, wrong
   touch-off sign, short blind-tap drill, spindle-to-table stack overflow,
   unsupported slender shaft (`unknown`, not `pass`). Measured warning burden
   on the four good plans.
2. **M2 — kernel spike.** FreeCADCmd on the four real STEPs: descriptor
   resolution against sidecar features, bounding boxes, one reach check for a
   named milling op. Go/no-go for M3.
3. **M3 — fixtures + restricted geometry rules** (vise+parallels, collet/chuck,
   centres; rank 5–6 rules), only if M2 passes.
4. **M4 — harmonic-analyzer integration.** `cad/config/process/<part>.yaml` +
   spec sidecar export; a flat `check:process_<stem>` doit task (the existing
   checks are flat `check:<name>`, not nested) with `file_dep` on plan, spec,
   inventory, cited tables, the STEP and the prechips version. Note: process
   YAML under `cad/config/` is absorbed by `_buildgraph`'s whole-config
   fallback (`**`) and by `check:math`/`check:config`/`check:recipe`'s broad
   YAML deps — so CAD *leaves* keep their keys, but those checks re-run.
   Either accept that or keep the process files outside `cad/config/`
   (e.g. `cad/process/`), which is the cleaner cut.
5. **M5 — advisory physics and adapters**, each behind its own citation.

## 8. Risks

- Sidecar authorship: someone on the CAD side must export and verify it
  against the native drawing. Without it, prechips degrades to §4 ranks 1–3
  on plan+inventory only — still useful, still honest.
- Inventory measurement debt: every `verify: true` is an `unknown` until
  measured; the first run's output is a measuring list, not a verdict.
- FreeCAD/OCC behaviour on SolidWorks AP214 exports is unproven here (M2).
- Bench verification is the only proof of executability; `verification.status`
  flips to `bench_verified` only with a logbook entry, and any change to the
  STEP hash, plan or inventory resets it to `planned`.
