# Prechips prototype

Prechips restarted at **v0.10**. The current milestone is **v0.10 vise holding** (package 0.10.1; the restart label and this milestone share the number): the `vise_holding` check. It remains a prototype until Pedro finds it useful, not a machining certification system.

## Scope and milestones

- Develop in small, usable milestones. Pedro approves each milestone. Never work more than three milestones ahead of his last review.
- v0.10: a machine-readable manual-manufacturing process in TOML and a simple CLI producing printable traveler HTML for harmonic-analyzer's `ch_rocker_arm_tl_oblique_base_bar`.
- v0.2: `pro` and `hobby` presets plus custom TOML profiles. Enforcement is limited to setup-rendering completeness. Hobby includes practical authored SVG setup diagrams and selects optional operation `instruction_detailed` in place of `instruction`; custom profiles opt in with `detailed_instructions`. No CAD/FreeCAD requirement. Pro is the default.
- v0.3: bind dimensions, drawing identity and diagram feature geometry to the selected CAD/drawing export. Keep process choices explicit. Prefer released data over importing CAD code or reconstructing dimensions from drawings.
- v0.4: both built-in profiles compare declared rectangular blank dimensions with the CAD nominal envelope in explicit length/width/thickness correspondence; custom profiles may omit `stock_fit`. No automatic stock rotation, parent-bar yield, machining allowance or machining simulation. Successful checks add nothing to the sheet.
- v0.5: explicit part adapters bind finished dimensions, setup coordinates and inspection limits from the selected feature manifests. Keep source geometry and requirements separate from authored tooling, allowances, fit-to-assembly choices and gauges. The bracket manifest remains illustrative example intent, not a released dimensioned drawing. These adapters do not imply generated setup pictures.
- v0.6: plans may explicitly reference one shared shop TOML for tool descriptions and named material/tool cutting settings. Local fields override shared fields individually. Do not infer identities, calculate recommendations or parse settings out of operation prose.
- v0.7: built-in hobby supports the pivot shaft's four CAD-manifest-driven setup elevations. Keep arriving material, active cuts, datums and support orientation consistent with the plan; fixture symbols are schematic. Round-stock diameter covers nominal shaft geometry, and available length covers the authored sawn-blank demand, not a fixed fit-to-assembly finish length. No native CAD engine or general setup simulation.
- v0.8: declared-input checks read explicit structured plan fields and shop records (`machines`, `workholding`, `gauges`, `limits`); no geometry engine. Inputs are expected to be written by an AI agent and comprehensive: built-in profiles require every applicable setup and operation to declare each check's data or an explicit opt-out value. Use shop and plan values as written; do not add measured/unmeasured provenance. Each check is one module registered in `checks.py`, refuses before output, prints nothing on a pass and has its own `--disable-check` key. Calculated speeds, feeds and index settings print in place of authored values; an authored value still wins.
- v0.8 keys: `cutting_speeds`, `tool_sizing`, `indexing`, `gauge_capability`, `lathe_holding`, `machine_capacity`; `stock_fit` also covers the bracket and rocker CAD nominal envelopes against their sawn flat-bar blanks. The shaft's fit-scribe hold refuses `lathe_holding` (33.33 mm unsupported against 4 × Ø6.35 = 25.4 mm). Keep that refusal and its documented opt-out, as with Op 60; do not tune jaw offsets or limits to pass.
- v0.9: the base bar reads the v48 manifest (bar 1 alone carries the #12 bracket holes; rail stations are REF only: every hole is drilled at its centre measured on that bar's own rail, trimmed flush both ends; never measured R1 plus the REF pitch, per harmonic-analyzer's spec and the owner's R4 ruling). `harmonic_end_bracket` binds TL-28's two shared-axis #8-32 holes and their per-face thread zones and tap-tip marks; `harmonic_feed_lever` binds TL-26's envelope and two clearance holes. `examples/end-bracket.toml` and `examples/feed-lever.toml` transcribe the 2026-11-02 hand travelers. The feed lever refuses `tool_sizing` (hand-sheet 11/32 in drill under the Ø.344 minimum); keep that refusal and its documented opt-out. No backwards compatibility with older manifests; when a release changes the drawing, follow the manifest and record what changed.
- Base bar, bar 2: drawing sheet 2 swaps the rail and table seats, and the v48 manifest describes bar 1 only. Keep the per-bar face marks (bar 1 C'BORE SIDE, bar 2 RAIL SIDE), datums, rock test and inspect picture authored from the two sheets until the manifest exports bar 2. The 1/2 in end mill alone cuts the slots on the adapter's cutter-centre rectangle (offset e sideways and e past each arc centre); a plain side offset makes a short slot and must not be authored.
- The end-bracket adapter's thread zones and tap-tip marks are the single deliberate exception to "no values from prose": v48 states them only in drawing note text, so they are read with exact patterns and refused on any rewording or inch/mm disagreement. Do not add further prose parsing; replace this one with structured `thread_zone`/`tip_mark` fields once harmonic-analyzer exports them.
- v0.9 hobby: built-in hobby renders both jig parts with one `jig-*` picture per setup (`src/prechips/jig_diagrams.py`; the templates under `examples/diagrams/{end-bracket,feed-lever}/` are bare roots, the shell and legend are generated). Part geometry comes from adapter values; jaws, parallels, overhangs, edge-finder stations and kerf from authored parameters; fixture symbols are schematic. Each saw picture shows only its own sheet's blanks, so neither plan carries the other part's lengths. Keep each picture's holding, datum and active face consistent with its setup text, and keep hobby `instruction_detailed` to the hand sheets' part-specific methods (Y0 on the fixed jaw, tap tape flags, corner filing).
- v0.10 vise holding: `vise_holding` (`src/prechips/vise.py`) requires `vise_hold` on every non-lathe setup (`"other"`, a table, or an array for re-grips) against a `kind = "vise"` workholding record: opening, parallels below the jaws, grip ≥ `limits.vise_grip_min_mm` (Pedro's 6 mm house choice) and ≥ `limits.vise_grip_fraction_min` × part height (one-third, a cited rule of thumb, not a standard), centred (gripped-span midpoint within `limits.vise_centre_fraction_max` × half the jaw width of centre: the middle third, a house rule) or balanced (`balance = "twin_part"` or `"spacer"`; a twin must clear the jaw centre), rod against an unmachined moving-jaw face, no sawn face on the fixed jaw (house rule). Overhang is declared geometry only; no source gives an overhang limit, so rigidity is not judged. The end bracket holds both brackets per clamping, one at each jaw end (X0 left INNER END, XR right). Do not invent limits or retune holds to pass. Envelopes and jig pictures still read vise sizes from plan parameters that repeat the shop record.
- Turning gate: both built-in profiles enforce `turning_deflection`, with authored total-transverse-bending limits of 0.10 mm rough and 0.005 mm finish. Exceedance or missing applicable data fails before output; success and explicit opt-outs add no checker text, warnings or certificates to the traveler. Keep stock/diagram-only fixtures independent with explicit opt-outs where needed.
- Require explicit setup `machine_kind` and lathe-operation `cut_kind` coverage. Only declared continuous solid-round longitudinal cuts are modeled; facing, parting, grooves and attachment domes are explicitly `other`, not silently checked. Do not infer material identities, geometry or numeric feed from prose. Use typed CAD/process bindings for analysis data without changing printed output.
- Keep coefficients editable in packaged `turning.toml`; partial custom TOML overrides merge over defaults. Profile `turning_config` paths are profile-relative; `--turning-config` wins. Repeatable `--disable-check` removes selected enforcement, including `turning_deflection`, without sheet warnings; a disabled turning check intentionally does not read its config. Protect active default/override configuration inputs from output aliases. Per-cut `max_deflection_mm` may only tighten the configured phase limit.
- Default material conditions are rolled-hard aluminum (2014-T6 modulus proxy), medium brass (naval-brass modulus proxy), medium bronze (phosphor-bronze ASTM B159 modulus proxy), authored plain-carbon 160–180 HB for 1018 (SAE 1025 modulus proxy), and authored annealed tool-steel 200–250 HB for O1 (steel-family modulus proxy), never hardened O1. Keep the packaged handbook citations and proxy caveats; radial/tangential ratio 1.0 is authored, not a universal measurement.
- Preserve the shaft's actual feeds, DOCs, limits and support geometry. Limits apply to estimated radial bending at the tool (diameter error ≈ 2×); the tangential force is reported, not compared. Every cut declares the full traverse (`start_z_mm`/`end_z_mm`) and the retained extent (`kept_start_z_mm`/`kept_end_z_mm`, mandatory, never defaulted); the limit applies over the kept range, support validation covers the whole traverse, and refusals report both maxima. Bind kept bounds from CAD/process values (shaft: `north_apex_z`, `body_kept_end_z`). With them the journal passes and the body finish still refuses at Op 60 (about 0.009 mm radial just before follower engagement at Z152, inside the kept body). Do not tune data to manufacture a pass. Share authored longitudinal feed parameters between numeric analysis records and printed instructions/settings. Bound maximum DOC at final/minimum diameter without assuming a rough-pass order. This remains a static prototype screen, not measured diameter-error prediction, machine-compliance/chatter modeling or machining approval.
- Pro prints only what an experienced operator needs: tools, setups, feeds, speeds and inspections, with the dimensions and instructions necessary to perform them. No tutorials, repeated warnings, checker reports or internal identifiers. Omit routine technique and generic safety reminders ("lock head", "short stickout", "power off", stopping/retracting, cleaning/reseating); retain part-specific workholding, datums and cutting requirements.
- For a requested hobby method, author concise, actionable, part-specific `instruction_detailed` in the operation itself. It replaces the pro instruction, never follows or repeats it; retain shared settings and inspection limits. Explain unfamiliar attachment setup once, then reference that method with each later operation's own dimensions.
- Specify datum locations and acceptance dimensions, not generic measuring-tool technique. Pro omits edge-finder speeds, hand-feed instructions, tip-radius offsets and compensated inspection readings; hobby may explain a source-backed attachment measurement needed to carry out the job.
- The pro base-bar traveler must print on no more than two Letter pages at readable type size. Hobby may use extra pages for readable setup diagrams and requested specific methods. Use operator shorthand in pro; keep hobby detail nonduplicated and actionable. Do not print process-status notes such as "untried", "unverified" or certification commentary; state tooling, work instructions and inspection requirements directly.
- Number setups and operations. Use aligned tables for work instructions, cutting settings, coordinates and inspection criteria; keep full tool specifications in the tooling list and short labels in operations.
- Assume normal shop equipment (collets, drill chuck, calipers, micrometer, rule, indicator, marker, dead-blow). Omit it from the tool list; list specified cutting tools and job-specific equipment instead.
- The previous implementation is preserved on `archive/pre-v0.10-2026-11-08`. Pull old code, data-schema ideas or FreeCAD logic only when a concrete approved milestone needs them. Do not migrate the old architecture wholesale.

## Keep it small

- No integrity checks, SHA-256 machinery, validation certificates, attestation systems, evidence bundles or speculative infrastructure.
- No general checker/rule framework, geometry engine, telemetry or inventory database unless an approved milestone needs it. Profiles select implemented features only; CAD bindings and the targeted stock-fit comparison do not justify restoring the legacy checker.
- Basic input errors and HTML escaping are ordinary functionality, not a validation subsystem.
- Do not invent machining dimensions, feeds, speeds, stock, tooling availability or inspection results. Use source-backed instructions; mark missing operating facts plainly and locally. A rendered sheet is not machining approval.
- Prefer the standard library and straightforward code. Keep the authored process readable without knowing the implementation.

## Development

- Use Python 3.12+ and uv only for environments, dependency changes and execution. Keep `pyproject.toml` and `uv.lock` together.
- Tests: bare-minimum end-to-end smoke coverage, plus focused tests only for particularly fragile or complex logic. No golden-output bureaucracy, source-text assertions, exhaustive combinatorics or heavyweight validation suites.
- Run the real CLI and inspect the actual print layout before delivering a milestone. Do not confuse automated tests with physical shop verification.
- Update the short README and schema documentation when their public contract changes. Do not grow a documentation hierarchy for this prototype.
- Preserve unrelated user files and local outputs. Archive source history before removing superseded tracked files.
- Publish changes in a PR; do not merge a milestone before Pedro approves it.
